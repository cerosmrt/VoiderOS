EDITING / UNDO
--------------
- Undo/redo (Ctrl+Z / Ctrl+Shift+Z) — SCOPED, ready to build. Decisions made:
    * Scope = TEXT CHANGES ONLY. Navigation and view switches are NOT undoable
      (decided against — Ctrl+Z should restore text, not bounce views).
    * Granularity = per EDIT-BURST. Typing on one line collapses into one undo
      step (closes when you move off the line / switch file-view / do a
      structural op). Structural ops (delete-to-zero, split/join, F5 dispatch,
      reorder, rename) are each their own step.
  Design (capture at the write chokepoint):
    * Every text mutation funnels through _atomic_write_lines / auto_save_circular.
      A small UndoManager captures file state THERE → covers every mutation
      without instrumenting scattered sites.
    * Two stacks (undo/redo). Each entry = a transaction holding per-file
      {before, after} line-lists. F5 dispatch touches 2 files (source+target),
      grouped so one Ctrl+Z undoes the whole move.
    * Coalescing: auto_save_circular gets an optional coalesce key. _doc_live_save
      passes ('line', index) so consecutive same-line saves merge; structural ops
      pass no key → own entry.
    * Apply undo/redo by writing through the SAME atomic primitive (temp+replace+
      IPC) — undo can't corrupt, just a reversible atomic write. If the restored
      file is the current doc, reload line_ring + refresh view (reuse the
      cross-instance reload path). Git snapshots remain the backstop.
    * In-memory only (cleared on restart; git covers older history), cap ~100
      entries, drop oldest.
  Build order (TDD): (1) headless UndoManager core (push/coalesce/undo/redo/
    transaction grouping) with full unit tests; (2) wire capture into write layer
    + coalesce key into _doc_live_save; (3) Ctrl+Z/Ctrl+Shift+Z in key router +
    reload-after-restore. v1 = F2 doc edits only; extend to F5 dispatch + F3
    library ops in a follow-up (cross-file transactions).

F3 / LIBRARY
------------
- Ctrl+D — duplicate (context-sensitive):
  * In F2 (doc view): duplicate the current line, inserting the copy directly
    below it; cursor moves to the copy. Autosave + content-undo (Ctrl+Z).
  * In F3 (library): duplicate the highlighted chapter file — write a copy next
    to it (e.g. "<name>-2.txt", uniquified) and insert its entry right after the
    original in the library. Atomic write; undoable via the F3 library-undo lane
    (wrap in _f3_undo_begin/_f3_undo_file/_f3_undo_commit like the other F3 ops).
  Note: Ctrl+Shift+D is the (currently broken) dispatch binding — keep Ctrl+D
  distinct from it. Also confirm Ctrl+D doesn't collide with an existing editor
  binding (e.g. deleteLineToZero) before wiring.

- New-entry name clash → jump to the existing chapter (no phantom duplicate row).
  DECIDED: the EXISTING chapter always survives (keeps its slot + name); the
  intruder is absorbed. Since a new entry is EMPTY when named, "merge" here is
  simply: put the cursor on the existing chapter, do NOT add a second row.
  Today _book_confirm_edit (f3_mixin.py ~200) on Shift+Enter, if the typed name
  already exists, does NOT overwrite the file but STILL adds a second library row
  pointing at the same file — F3 shows the name twice, both editing the same text.
  That is the bug to fix (jump instead of duplicate row).
  DECIDED scope of "same name → append":
    * Split (/name marker): append into existing — already works (explicit intent).
    * New-entry over existing name: just jump (empty, nothing to lose).
    * RENAME to an existing name: KEEP REFUSING (today's behaviour). Do NOT
      auto-merge — a real chapter with content would silently vanish from view,
      which is surprising/dangerous. No change needed here. The DELIBERATE way to
      combine two chapters already exists: enclose both under a dot and MERGE
      them (Ctrl+Shift+M). So refusing the rename loses nothing.
  Related duplicate-name hardening (surfaced together; C4 from the integrity
  audit): many ops resolve a chapter by bare name via .index(fname) → FIRST match,
  so duplicate names make the cursor/selection (A1 restore, B3 reload) and edits
  land on the wrong row; and two files sharing a basename across I/ subfolders
  leave the second shadowed/unreachable (_build_library_path_cache keeps the
  first, warns "Duplicate basename"). Longer-term: resolve by (index+name) or a
  stable id instead of bare name.

- F3 dot separator Ctrl+Delete: pressing Ctrl+Delete on a '.' line in F3 (the
  separator between two chapter groups) should delete only that separator, merging
